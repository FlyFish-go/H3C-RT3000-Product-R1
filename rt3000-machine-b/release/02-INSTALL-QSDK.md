# RT3000 刷机教程 · 第二部分：安装 QSDK

[← 教程总览](INSTALL.md)

> **适用范围**：仅在 RT3000 Machine-B（`GD5F1GQ5REYIG` NAND、原厂 `RT3000V100D009`）验证。A/C 样机以及 RW3000、RC3000、NX30 请勿套用镜像或刷写命令；无法确认硬件时先停下。

## 0. 开始前必须知道的

### 0.1 我们在往哪里写

设备有两个系统槽位：

| 槽位 | 分区 | 现在装什么 | 本部分会动它吗 |
|---|---|---|---|
| A | `mtd15` | **原厂系统** | ❌ **绝不碰** |
| B | `mtd16` | 全新原厂设备上预期为空；曾刷过机则可能已有内容 | ✅ 核对后写 QSDK 到这里 |

**`mtd15` 全程不碰** —— 它是你的退路。
**如果 `mtd16` 已有需要保留的系统或数据，不要继续安装。** 先按第 4 节核对现状。

### 0.2 有哪些保护机制，以及它们的**边界**

> ⚠️ **先看这一节的「尚未验证」部分** —— 不要基于过强的假设去操作。

#### 保护一：写入前把启动目标切到原厂

**写入 `mtd16` 之前，会把 selector 先切到原厂。**

```
① 确认当前在原厂槽        ← 见第 4 节
② 把启动目标切成「原厂」   ← 此后若写入失败，重启会进原厂
③ 写入 mtd16
④ 校验写入的内容
⑤ 校验通过 → 把启动目标切成「QSDK」
⑥ 重启
```

**在 ② 和 ⑤ 之间**，启动目标指着原厂。
所以**如果写入/校验阶段失败**，重启后设备会尝试启动原厂。

#### 保护二：原厂系统（`mtd15`）不被写入

我们从头到尾**不写 `mtd15`**。所以：

- 原厂系统的**内容**始终保留
- 即使 QSDK 装坏了，原厂的数据还在设备里

---

#### ⚠️ 这些保护「不覆盖」什么（重要）

**保护和「一定能救回来」是两回事。** 以下情况本教程**尚未验证**或**无法保证**：

| 情况 | 实际状态 |
|---|---|
| **切到 QSDK 后启动失败，是否自动回退到原厂** | 🔴 **未验证**。我们没有实测过「QSDK 启动失败 → 自动回落原厂」这条路径。机制上 U-Boot 会读取 selector，但**失败时它是否/如何回退，未经验证**。 |
| **原厂内容完好 ⇒ 无需串口就能切回原厂** | 🔴 **不成立**。切回需要一个能运行命令的系统：QSDK 起不来、原厂又没在运行时，**只能靠串口 + U-Boot**（见第五部分）。 |
| **写入过程中断电** | 🟡 **可能**没事（启动目标还在原厂），但这只是机制推断，**未在真机上验证过断电场景**。 |
| **两个系统都无法启动** | 🔴 需要 TTL 串口救援。**原厂数据完好 ≠ 设备一定能自己起来**。 |

> 📌 **一句话**：
> **保护机制能降低风险，但不能替代备份和串口救援准备。**
>
> 尤其注意：**「原厂系统没被写过」不等于「一定能回到原厂」** ——
> 回到原厂需要一个能执行切换命令的运行环境。

### 0.3 一定要看的风险提示

虽然有两个保护机制，但仍要注意：

| 风险 | 说明 |
|---|---|
| **写错分区** | 误写 `mtd15` → **原厂内容被覆盖**。所以第 4 节的检查必须做。 |
| **文件损坏** | 所以第 3 节必须校验哈希、第 5.5 节必须读回校验。 |
| **写入中断电** | 机制上启动目标仍指向原厂，但**断电场景未实测**。尽量避免。 |
| **QSDK 装好后启动失败** | 🔴 **自动回退到原厂未验证**。此时可能需要串口救援（第五部分）。 |
| **两个系统都起不来** | 🔴 需要 **TTL 串口 + U-Boot**。**没有串口线时无法自行恢复。** |

> ⚠️ **不要跳过第 3 节和第 4 节。** 这两步是防呆的，花不了 1 分钟。

## 1. 准备刷机文件

需要**两个文件**：

| 文件 | 大小 | 作用 |
|---|---|---|
| `factory.ubi` | 约 13 MB | **QSDK 系统镜像**（写入设备用） |
| `rt3bcwrite` | 约 12 KB | **槽位切换工具**（原厂固件里没有，必须传进去） |

### 1.1 从哪里获得

**`factory.ubi`**：从本项目的产物中获取。

| 版本 | SHA-256 |
|---|---|
| **r5**（推荐，含 WiFi 修复） | `80e99811887ec3bedaf648a32954d93fc5e1482ab70605d6e41d791ce181c529` |

**`rt3bcwrite`**：同样从项目产物获取。

| SHA-256 |
|---|
| `e23d8634af3fb20a5c383aa22ad2dc65752133ffd91d3715a70df5121d0789f5` |

> 📌 **务必用上面这个 `rt3bcwrite`** —— 它是专门为这台设备写的槽位切换工具，
> 带「写后立即校验」的双副本事务保护。**不要用其它来源的版本。**

### 1.2 放到一个文件夹里

把两个文件放在**同一个文件夹**，例如：

```
D:\RT3000\
├── factory.ubi
└── rt3bcwrite
```

> 📌 **关于文件名**：
> - `rt3bcwrite` **必须**保持这个文件名（bat 脚本按这个名检查）
> - `.ubi` 镜像**叫什么都可以**（脚本会自动识别），但**下载到设备后建议统一命名为 `factory.ubi`**
>   —— 这样后面第 5 节的命令不用改。

## 2. 把文件送进设备

### 2.1 为什么需要这一步

此时设备应**正在运行原厂固件**，但临时目录里还没有这两个文件。而且：

> **原厂固件没有任何「上传文件」的入口。**
>
> 所以不是「我们推文件给设备」，而是「**设备主动来拉**」。

**做法**：在你的电脑上开一个临时的「文件服务器」，然后让设备去下载。

### 2.2 步骤

#### 第一步：在电脑上起一个文件服务

**Windows（推荐，用现成脚本）**：

项目提供了一个脚本 `1-启动文件服务器.bat`。把它放到**和刷机文件同一个文件夹**，右键以管理员身份运行（脚本会放行防火墙）。

请使用只放本次 `rt3bcwrite` 和已校验镜像的**专用临时文件夹**，不要从含原厂配置备份、个人文件或其他私密资料的目录启动服务。它会通过 HTTP 暴露当前目录，仅在可信局域网短时运行；下载完成就停止，并清理防火墙规则。

**脚本会依次做**：
1. 列出电脑的局域网 IP；若有多个，选择设备能够访问的那个
2. 列出目录中的 `.ubi` 镜像；若有多个，核对 SHA-256 后选择
3. 检查 `rt3bcwrite` 和所选镜像是否存在
4. 放行防火墙的 TCP 8899 端口并启动服务

**运行后会看到**类似下列信息（IP 和镜像文件名以实际窗口为准）：

```text
[1/4] 检测本机网络地址 ...
      [1] 192.168.1.100
      已选择: 192.168.1.100
[2/4] 查找镜像文件 ...
      [1] openwrt-ipq50xx-arm-h3c_rt3000-squashfs-nand-factory.ubi  13107200 字节
      已选择: openwrt-ipq50xx-arm-h3c_rt3000-squashfs-nand-factory.ubi
[3/4] 检查文件 ...
      OK  rt3bcwrite  12287 字节
      OK  openwrt-ipq50xx-arm-h3c_rt3000-squashfs-nand-factory.ubi  13107200 字节
[4/4] 放行防火墙 8899 端口 ...
      OK

  在设备的 telnet 窗口里执行下面两条命令：
    cd /tmp
    wget http://192.168.1.100:8899/rt3bcwrite -O /tmp/rt3bcwrite
    wget http://192.168.1.100:8899/openwrt-ipq50xx-arm-h3c_rt3000-squashfs-nand-factory.ubi -O /tmp/factory.ubi

  服务已启动。保持本窗口开着，不要关闭！
```

> 🔴 **下载完成前这个窗口必须一直开着**。下载结束后按 `Ctrl+C` 停止服务，或直接关窗口。
> 脚本创建的 `RT3000-Flash-HTTP` 防火墙规则可能保留；在管理员命令提示符执行
> `netsh advfirewall firewall delete rule name="RT3000-Flash-HTTP"` 清理。

#### 第二步：在设备的 telnet 窗口里下载

> **注意**：这一步要在**设备**上执行（你第一部分拿到的 `root@OpenWrt:/#` 那个窗口），
> 不是在电脑上。

**把脚本打印的 IP 填进去**（上面示例是 `192.168.1.100`，**你的可能不同**）：

```sh
cd /tmp

wget http://192.168.1.100:8899/rt3bcwrite -O /tmp/rt3bcwrite

wget http://192.168.1.100:8899/openwrt-ipq50xx-arm-h3c_rt3000-squashfs-nand-factory.ubi -O /tmp/factory.ubi
```

> 📌 **第二条命令里的文件名**：用你服务器窗口里打印的那个（脚本会自动识别你放的 `.ubi` 文件）。
> `-O /tmp/factory.ubi` 表示**下载后重命名为 `factory.ubi`** —— 保持这个名字，
> 后面第 5 节的命令就不需要改。
>
> 例如你的文件叫 `openwrt-xxx-factory.ubi`，那就写：
> ```sh
> wget http://192.168.1.100:8899/openwrt-xxx-factory.ubi -O /tmp/factory.ubi
> ```

**期望输出**（原厂 BusyBox 的下载进度示例）：

```text
Connecting to 192.168.1.100:8899 (192.168.1.100:8899)
rt3bcwrite           100% |********************************| 12287  0:00:00 ETA
```

下载成功仍要按下一节核对两个文件的 SHA-256；单凭进度条不足以证明镜像正确。

> 💡 **如果文件名或大小不对**，说明 IP 或文件名写错了。重新检查。

## 3. 校验文件

### 3.1 算哈希

```sh
sha256sum /tmp/rt3bcwrite /tmp/factory.ubi
```

### 3.2 必须与下面完全一致

```
e23d8634af3fb20a5c383aa22ad2dc65752133ffd91d3715a70df5121d0789f5  /tmp/rt3bcwrite
80e99811887ec3bedaf648a32954d93fc5e1482ab70605d6e41d791ce181c529  /tmp/factory.ubi
```

> ✅ **两个都对得上 → 继续**
>
> ❌ **任何一个不对 → 停下！** 文件身份不符，可能是下载不完整、文件选错或电脑上的源文件本身不对。
> 先核对电脑上的源文件，再重新下载和校验。

### 3.3 顺便给工具加执行权限

```sh
chmod +x /tmp/rt3bcwrite
```

## 4. 保命检查：确认「现在跑的」和「下次启动的」都是原厂

> ⚠️ **这一步不能跳过。** 它要确认三件事，缺一不可：
>
> 1. **当前实际运行的是原厂系统**（不是 QSDK）
> 2. **下次启动目标指向原厂**（保命）
> 3. **`mtd16` 的 UBI 现状**（判断能否直接写）

### 4.1 ⚠️ 先破除一个误解：selector ≠ 当前运行的系统

**selector 表示的是「下次启动去哪个槽」，不是「现在跑的是什么」。**

这两者**可能不一致**：

| 情况 | selector | 实际运行 | 说明 |
|---|---|---|---|
| 正常 | 0（原厂） | 原厂 | 一致 |
| **刚切完还没重启** | 1（QSDK） | **原厂** | **不一致！** |

**为什么会不一致**：selector 是**写进 flash 的持久值**，
而当前运行的系统是**开机那一刻**决定的。中间改了 selector，不会影响正在运行的系统。

> 🔴 **所以不能只看 selector 就认为自己在原厂。**
> 必须**另外独立确认**当前运行的是什么系统。

### 4.2 第 1 步：确认实际运行的系统

**原厂固件和 QSDK 有几个稳定可辨的区别**，逐个查：

```sh
# ① 内核版本
uname -r

# ② 分区表命名（最能说明问题）
cat /proc/mtd | grep -E "mtd1[56]"
```

**判定表**：

| 检查 | 原厂系统 | QSDK |
|---|---|---|
| `uname -r` | `4.4.60` | `5.4.164` |
| `mtd15` 的名字 | `"rootfs"` | `"oem_rootfs"` |
| `mtd16` 的名字 | `"rootfs_1"` | `"rootfs"` |

**必须看到「原厂」那一列**：

```
4.4.60
mtd15: 02800000 00020000 "rootfs"
mtd16: 02800000 00020000 "rootfs_1"
```

> 🛑 **如果 `uname -r` 显示 `5.4.164`**，说明你**正在 QSDK 里** ——
> 此时**不能**执行第 5 节的 `ubiformat`（那会擦掉你正在运行的系统）。
>
> **正确做法**：先用[第三部分](03-SWITCH-SYSTEMS.md#2-qsdk-原厂)切回原厂，
> **重启**后再继续。

### 4.3 第 2 步：确认根文件系统来自哪里

```sh
# 看根文件系统挂载情况
mount | grep -E " / |rootfs"

# 看启动参数（部分固件会写明根设备）
cat /proc/cmdline
```

**原厂的典型输出**：

```
/dev/root on / type squashfs (ro,relatime)
```

> 📌 **这一步是辅助确认**。不同固件输出格式可能不同，
> **以 4.2 节的 `uname -r` + 分区命名为主要依据。**

### 4.4 第 3 步：查看 selector（启动目标）

**注意**：原厂固件里的 musl 加载器叫 `/lib/ld-musl-arm.so.1`，
而我们的工具需要 `/lib/ld-musl-armhf.so.1`（**多了 `hf`**）。

直接运行会报错：

```
$ /tmp/rt3bcwrite --show
/bin/sh: /tmp/rt3bcwrite: not found      ← 实际是找不到加载器
```

**所以必须显式指定加载器**：

```sh
/lib/ld-musl-arm.so.1 /tmp/rt3bcwrite --show
```

> 📌 **在原厂里的每一条 `rt3bcwrite` 命令都要加这个前缀。**
> （QSDK 里不需要 —— QSDK 的加载器名字是对的。）

**期望输出**：

```
mtd3(0:BOOTCONFIG1) rootfs selector = 0x00000000
mtd2(0:BOOTCONFIG) rootfs selector = 0x00000000
copies_agree=YES
current_slot=A(rootfs/OEM)
```

**逐行确认**：

| 输出 | 含义 | 要求 |
|---|---|---|
| `mtd3 = 0x00000000` | 副本一 | ✅ 必须是 `0x00000000` |
| `mtd2 = 0x00000000` | 副本二 | ✅ 必须是 `0x00000000` |
| `copies_agree=YES` | 两副本一致 | ✅ 必须是 `YES` |
| `current_slot=A(rootfs/OEM)` | **selector 指向**原厂 | ✅ |

> ⚠️ **`current_slot=A(rootfs/OEM)` 只说明「selector 指向原厂」，
> 不说明「当前运行的是原厂」。** 后者由 4.2 节确认。
>
> 🛑 **如果显示 `0x00000001`**：selector 指向 QSDK。
> 那意味着**下次启动会进 QSDK** —— 此时写 `mtd16` 是危险的
> （可能覆盖你打算保留的系统）。**先确认清楚再继续。**

### 4.5 第 4 步：查看 mtd16 的 UBI 现状（只读）

**写入前先看 `mtd16` 现在是什么状态** —— 这决定第 5 节要不要先 detach。

```sh
# ① mtd16 是否被 UBI 占用？（只读查询）
cat /sys/devices/virtual/ubi/ubi*/mtd_num 2>/dev/null | while read n; do
    echo "有 ubi 设备挂在 mtd$n"
done

# ② 更直观的方式：看 UBI 设备列表
for d in /sys/devices/virtual/ubi/ubi*; do
    [ -f "$d/mtd_num" ] || continue
    echo "$(basename $d) -> mtd$(cat $d/mtd_num 2>/dev/null)"
done

# ③ mtd16 上有没有 UBI 魔数（判断是否曾经格式化过）
dd if=/dev/mtd16 bs=1 count=4 2>/dev/null | hexdump -C
```

**怎么读结果**：

| 现象 | 含义 | 第 5 节要怎么做 |
|---|---|---|
| 没有 ubi 设备挂在 `mtd16` | 未被占用 | 满足 4.6 全部条件后可直接 `ubiformat` |
| **有** ubi 设备挂在 `mtd16`（如 `ubi4 -> mtd16`） | 被占用 | **先 `ubidetach`**（见 5.3） |
| `dd` 输出 `55 42 49 23`（`UBI#`） | 曾是 UBI 格式 | 正常，`ubiformat` 会覆盖 |
| `dd` 输出全 `ff` | 空白分区 | 正常，首次安装的典型状态 |

> ✅ **这里全部是只读命令**（`cat` / `ls` / `dd` 读），
> **不会修改任何数据**。
>
> ⚠️ **不要**用「再执行一次 `ubiformat` 看能不能过」来探测状态 ——
> 那是**擦写操作**，会在你还没准备好时就破坏数据。

### 4.6 四项检查汇总

**继续之前，必须同时满足**：

| # | 检查 | 要求 | 依据 |
|---|---|---|---|
| 1 | `uname -r` | `4.4.60`（**原厂**） | 4.2 |
| 2 | `/proc/mtd` 命名 | `rootfs` / `rootfs_1` | 4.2 |
| 3 | `rt3bcwrite --show` | `0x00000000` + `copies_agree=YES` | 4.4 |
| 4 | `mtd16` UBI 现状 | 已记录（决定是否 detach） | 4.5 |

> 🛑 **任何一项不符 → 停下，不要执行第 5 节。**

## 5. 写入 QSDK

> ⚠️ **本节会手动擦除并写入第二槽位。** 第四部分的系统内升级也会写入该槽位。
> 请先完成第 4 节的四项检查。

### 5.1 如果 mtd16 被 UBI 占用，先分离

**依据第 4.5 节的检查结果**：

| 4.5 的检查结果 | 现在怎么做 |
|---|---|
| 没有 ubi 设备挂在 `mtd16` | ✅ 跳过本节，直接到 5.2 |
| **有**（如 `ubi4 -> mtd16`） | 执行下面的 `ubidetach` |

```sh
ubidetach -m 16
```

**然后必须用只读方式确认分离成功**：

```sh
# 再看一次 UBI 映射（只读）
for d in /sys/devices/virtual/ubi/ubi*; do
    [ -f "$d/mtd_num" ] || continue
    echo "$(basename $d) -> mtd$(cat $d/mtd_num 2>/dev/null)"
done
```

**期望**：输出里**不再有** `-> mtd16`。

> ⚠️ **`ubidetach` 可能报错 `Invalid argument`（返回码 255）——
> 这是已知现象，不代表失败。**
>
> 🔴 **但不要用「再跑一次 `ubiformat` 看能不能过」来判断分离是否成功** ——
> `ubiformat` 是**擦写操作**，用它探测状态会在你没准备好时就破坏数据。
>
> ✅ **正确做法**：用上面的**只读** `/sys` 查询确认。

### 5.2 记录写入前的基线

**为了后面能验证「写进去了」，先记录镜像自身的身份**：

```sh
sha256sum /tmp/factory.ubi
```

**必须是**（r5）：

```
80e99811887ec3bedaf648a32954d93fc5e1482ab70605d6e41d791ce181c529  /tmp/factory.ubi
```

> ✅ **这个哈希只说明「你手上的文件是对的」**，
> **不说明「写进 NAND 的内容是对的」** —— 后者要靠 5.5 节的读回校验。

### 5.3 执行写入

```sh
ubiformat /dev/mtd16 -y -f /tmp/factory.ubi
```

**参数说明**：

| 参数 | 作用 |
|---|---|
| `/dev/mtd16` | 目标分区（**第二个槽位**） |
| `-y` | 不交互确认 |
| `-f /tmp/factory.ubi` | 要写入的镜像 |

> ⚠️ **再次确认 `/dev/mtd16` 拼写正确。**
> 写成 `mtd15` 会擦掉原厂系统。

**这个命令做的事**：把 `mtd16` 整块擦除，写入完整镜像，**一步到位**
（不需要手动建卷/attach）。

### 5.4 判断写入是否成功

#### ⚠️ 先说明：`ubiformat` 的输出因版本而异

**不同版本的 `ubiformat` 打印的进度行不一样。**
所以**不要**把某一句固定文案当作「必须出现」的判据 ——
那样会在版本不同时误判。

**本教程在真机上记录到的输出**（供你对照，**不是要求逐字匹配**）：

```
ubiformat: mtd16 (nand), size 41943040 bytes (40.0 MiB), 320 eraseblocks of 131072 bytes (128.0 KiB), min. I/O size 2048 bytes
libscan: scanning eraseblock 319 -- 100 % complete
ubiformat: 320 eraseblocks have valid erase counter, mean value is 7
ubiformat: flashing eraseblock 88 -- 100 % complete
ubiformat: formatting eraseblock 319 -- 100 % complete
```

> 📌 **注意几件事**：
> - `320 eraseblocks` 是**分区**的擦除块总数（40 MiB ÷ 128 KiB）
> - 而 13,107,200 字节的镜像**只相当于 100 个块** ——
>   所以「格式化 320 块」和「写入 100 块」是两回事，**输出里的数字不必相同**
> - `mean value` 后面那个数字是擦除计数均值，**每次都不一样**，不用管
> - 进度百分比会滚动很多行，可能被截断

#### ✅ 正确的成功判定

**以下面三条为准**，而不是某句文案：

| # | 判据 | 怎么查 | 说明 |
|---|---|---|---|
| **1** | **命令退出码为 `0`** | 紧跟着执行 `echo $?` | ⭐ **最主要依据** |
| **2** | **没有真正的错误信息** | 看输出里有没有 `error` / `failed` / `cannot` | 见下方说明 |
| **3** | **载荷读回校验通过** | 见 5.5 节 | ⭐ **最终判定** |

```sh
ubiformat /dev/mtd16 -y -f /tmp/factory.ubi
echo "退出码: $?"
```

**期望**：

```
退出码: 0
```

> ✅ **退出码 `0` + 5.5 节读回哈希匹配 = 写入成功。**
> 这才是完整的判定链，不依赖任何一句具体的提示文案。

#### ⚠️ 关于「看到 bad / error 就判定失败」

**不要这样做。** 有些字样是**正常的**，不代表失败：

| 字样 | 是否代表失败 | 说明 |
|---|---|---|
| `bad PEBs` | ❌ **不一定** | NAND 出厂就可能有坏块，工具会跳过；只要不超出预留数量就正常 |
| `corrupted PEBs` | ⚠️ **需看数量** | 少量且工具继续完成 → 通常可接受；大量或工具中止 → 失败 |
| `error` / `failed` / `cannot` | ✅ **是失败** | 真正的错误 |
| `Invalid argument`（来自 `ubidetach`） | ❌ **不是** | 已知现象，见 5.1 节 |

**判断原则**：**以退出码和读回校验为准**，不要靠关键词猜测。

#### 耗时

**约 1~2 分钟。** 耐心等它跑完，**不要中断**。

#### 可能遇到的报错

**`please, first detach mtd16 (/dev/mtd16) from ubi4`**

→ 说明 5.1 的分离没做到位。**回到 5.1 重新处理。**

**其它报错** → 记下完整输出和退出码，不要盲目重试。

### 5.5 🔍 读回校验（必做）

> **这是本教程采用的写后 NAND 载荷核验方法。**
> `ubiformat` 的成功只代表它把数据发出去了，不代表 NAND 上的内容完好。

#### 关于本节命令的验证状态

**本节分两部分，验证程度不同**：

| 部分 | 状态 |
|---|---|
| **校验参数**（卷长度 + SHA-256） | ✅ **已核对**：从 r5 镜像中解析卷、按长度截取、计算哈希，与镜像清单一致 |
| **下面这套操作命令**（`ubiattach` → 核对或创建节点 → `head`） | ✅ **2026-09-23 原厂真机复走**：`ubi4 -> mtd16`，两个卷名与设备号正确，按有效载荷长度读回的 SHA-256 均匹配；节点已自动存在，本次无需执行条件性的 `mknod` |

> 本次真机 `ubidetach -m 16` 报 `Invalid argument`，随后 `/sys` 只读查询确认 `mtd16` 已不再挂载。异常时仍须以实际映射为准，不要据报错或文档示例猜测结果。

#### 原理

`factory.ubi` 里有三个卷，其中两个有**已知的载荷哈希**：

| 卷 | 卷 ID | 载荷长度 | SHA-256 |
|---|---|---|---|
| `kernel` | 0 | 3474820 | `7a7c048e92bcd53bfdba554770195adbbaf4cf4deb0d383d4f3c85ba881c31c9` |
| `ubi_rootfs` | 1 | 8810094 | `31115a4c01c29357f6ed1e27a1f5007ef6e25904342054be48542610c5605f74` |

**做法**：`ubiattach` 挂上 `mtd16`，把这两个卷读回来算哈希，与上表比对。

#### 连接并建节点

> ⚠️ **每一步都要看输出。** 下面是命令 + 「正常应该看到什么 / 异常怎么办」。

##### ① 挂载 mtd16

```sh
ubiattach -m 16 -O 2048
echo "退出码: $?"
```

**正常**：退出码 `0`，并打印类似 `UBI device number 4, total 320 LEBs`。

**异常**：

| 现象 | 含义 | 处理 |
|---|---|---|
| `Device or resource busy` | 已经被 attach 了 | 跳到 ② 直接查询现有映射 |
| `error` 且退出码非 0 | attach 失败 | **停下**，检查 `mtd16` 是否已被写入 |

##### ② 查它被分配成哪个 ubiN（**不要假设是 ubi0**）

```sh
for d in /sys/devices/virtual/ubi/ubi*; do
    [ -f "$d/mtd_num" ] || continue
    echo "$(basename $d) -> mtd$(cat $d/mtd_num 2>/dev/null)"
done
```

**正常**：输出里有一行 `ubiN -> mtd16`。

**记下这个 `ubiN`**（例如 `ubi4`）：

```sh
UBI=ubi4        # ← 改成你上面看到的
```

**异常**：

| 现象 | 处理 |
|---|---|
| 没有任何 `-> mtd16` | **停下** —— attach 没成功 |
| 输出为空 | **停下** —— 该固件可能没有 `/sys/devices/virtual/ubi` |

##### ③ 确认卷名（确认真的是我们写的镜像）

```sh
for v in /sys/devices/virtual/ubi/$UBI/${UBI}_*; do
    [ -d "$v" ] || continue
    echo "$(basename $v): $(cat $v/name 2>/dev/null)  size=$(cat $v/data_bytes 2>/dev/null)"
done
```

**正常**：应该看到三个卷，名字分别是：

```
kernel        ← 卷 0
ubi_rootfs    ← 卷 1
rootfs_data   ← 卷 2
```

> 🔴 **如果卷名不对**（例如没有 `ubi_rootfs`，或名字完全不同）：
> **立刻停下** —— 说明 `mtd16` 里的内容不是你预期的镜像。
> 不要继续读回，也不要切换系统。

##### ④ 建 /dev 节点（**先检查现有节点，不要盲目 mknod**）

```sh
# 先看节点是否已存在、以及类型对不对
ls -la /dev/${UBI}_* 2>/dev/null || echo "（尚无节点，需要创建）"
```

**如果节点不存在**，创建：

```sh
for v in 0 1 2; do
    d=/sys/devices/virtual/ubi/$UBI/${UBI}_$v
    [ -d "$d" ] || continue
    dev=$(cat $d/dev)                   # 形如 "248:0"
    mknod /dev/${UBI}_$v c ${dev%:*} ${dev#*:}
done
```

**创建后核对**：

```sh
ls -la /dev/${UBI}_*
```

**必须满足**：

| 检查 | 要求 |
|---|---|
| 是**字符设备** | 权限位以 `c` 开头（如 `crw-------`） |
| **主:次设备号** | 与 `/sys/.../${UBI}_$v/dev` 里的值一致 |

> 🔴 **异常就停下**：
> - 如果节点**已存在但是块设备**（`b` 开头）→ 类型不对，**不要覆盖**，先停下排查
> - 如果**设备号与 sysfs 不符** → 节点是旧的/错的，**不要用**
>
> 创建节点是**写入操作**，用错参数可能指向别的设备。

#### 读回并比对

```sh
# kernel 卷（前 3474820 字节）
head -c 3474820 /dev/${UBI}_0 | sha256sum
# 期望: 7a7c048e92bcd53bfdba554770195adbbaf4cf4deb0d383d4f3c85ba881c31c9

# rootfs 卷（前 8810094 字节）
head -c 8810094 /dev/${UBI}_1 | sha256sum
# 期望: 31115a4c01c29357f6ed1e27a1f5007ef6e25904342054be48542610c5605f74
```

> ⚠️ **`head -c` 的长度数字必须写对**（7 位数，**不要多写一个 0**）。
> 写错长度会得出一个「看起来像但不匹配」的哈希，容易误判。
>
> 长度与哈希的对应关系来自 r5 镜像的清单，**不要凭记忆输入**。

**结果判读**：

| 情况 | 结论 | 下一步 |
|---|---|---|
| 两个哈希**都匹配** | ✅ 写入正确 | 继续第 6 节 |
| 任一**不匹配** | ❌ 写入有问题 | **停下**，见下方 |
| `head` 报错 / 读到 0 字节 | ❌ 卷没建好 | 检查 ③ 的 mknod |

> 🛑 **不匹配时不要切换到 QSDK。**
>
> 此时 `mtd16` 的内容不可信。**selector 仍指向原厂**，
> 你可以直接 `reboot` 回到原厂，然后重新执行第 5 节。
>
> **把两次哈希的完整输出记下来** —— 需要进一步排查。

#### 完成后分离

```sh
ubidetach -m 16
```

> 💡 **为什么要 detach**：让 `mtd16` 回到「干净未挂载」状态，
> 避免第 6 节切换后重启时的状态歧义。
> 若 `ubidetach` 报 `Invalid argument`，不要据此判断成败；按 5.1 节的 `/sys` 查询确认 `mtd16` 已不再挂载。

## 6. 切换到新系统并重启



### 6.1 切换启动目标

```sh
/lib/ld-musl-arm.so.1 /tmp/rt3bcwrite --set 1
```

**期望输出**：

```
PRE  mtd3(0:BOOTCONFIG1) = 0x00000000
PRE  mtd2(0:BOOTCONFIG) = 0x00000000
copy=mtd3 FIRST (redundant)
copy=mtd3 write=PASS verify=PASS
copy=mtd2 SECOND (primary)
copy=mtd2 write=PASS verify=PASS
POST mtd3(0:BOOTCONFIG1) = 0x00000001
```

### 6.2 逐行确认

|---|---|---|
| `write=PASS verify=PASS` | 每写一个副本后**立即读回校验** | ✅ 两个副本都要 PASS |
| `RESULT=PASS` | 最终结果 | ✅ 必须是 `PASS` |
| `both copies = 0x00000001` | 两个副本都指向 QSDK | ✅ |

> 🛑 **如果看到 `RESULT=FAIL`，不要重启。**
> 把输出发出来。`RESULT=FAIL` 说明 selector 没写成功，
> 此时重启可能进不去任何系统。

```
mtd2(0:BOOTCONFIG) rootfs selector = 0x00000001
copies_agree=YES
current_slot=B(rootfs_1/QSDK)
```

### 6.4 重启

```sh

```

> `sync` 把缓存写入存储，`reboot` 重启。**两条都要执行。**

**重启后 telnet 会断开** —— 这是正常的。

### 7.2 网络会变

| **LAN 地址** | 上游路由器分配的地址（如 `192.168.1.200`） | **`192.168.10.1`** |

> **解决办法**：把网线插到 **RT3000 的 LAN 口**。这样电脑会从设备拿到

### 7.3 怎么判断成功了

**方法一：看串口（如果有 TTL 线）**

启动日志里会出现：

```
     Description:  ARM OpenWrt Linux-5.4-qsdk-11.5.0.5      ← QSDK 内核
     Description:  ARM OpenWrt h3c_rt3000 device tree blob
```

**关键**：内核版本从 `Linux-4.4.60`（原厂）变成 **`Linux-5.4-qsdk-11.5.0.5`**。

**方法二：看网络**

把网线插到 LAN 口，然后用浏览器打开：

```
http://192.168.10.1
```

**看到 LuCI（OpenWrt 的网页界面）说明 QSDK 网页服务可达。**

**方法三：SSH 登录验证**

```bash
ssh root@192.168.10.1
```

> **首次登录密码为空** —— 直接回车。
> （QSDK 没有设默认密码，请**登录后尽快设置一个**。）

登录后执行：

```sh
uname -r
# 期望: 5.4.164

cat /tmp/sysinfo/board_name

```

### 7.4 完整验收清单

在 QSDK 里执行，逐项确认：

```sh
# 1. 系统身份

cat /tmp/sysinfo/board_name                 # h3c,rt3000

# 2. 系统是从 mtd16 启动的
cat /sys/class/ubi/ubi0/mtd_num             # 16
```

**期望结果**：

| `qsdk_slot_status` | `PASS` |
| 无线接口 | `wlan0` 和 `wlan1` 都有 SSID |
| `/overlay` | 约 19 M 可用 |

`rt3slot verify oem` 的 `PASS` 仅确认原厂分区几何、名称和 UBI 头，不证明原厂载荷完整或一定能启动。QSDK 的状态也要结合详细字段看实际覆盖范围；本部分第 5.5 节对写入后的 kernel/rootfs 做了指定长度的读回 SHA-256 校验。

## 常见问题

### Q1: `wget` 报 `can't connect to remote host`

**原因**：电脑上的文件服务器没起来 / 防火墙拦了 / IP 写错。

**排查**：

| 检查 | 方法 |
|---|---|
| 服务器窗口还开着吗 | 看那个黑色窗口是否还在 |
| 是不是管理员权限运行 | 不是的话，右键重新以管理员身份运行 |
| IP 对吗 | 用脚本窗口里打印的那个 IP |
| 两台设备能通吗 | 在设备上 `ping <电脑IP>` |

> 💡 **诊断技巧**：下载失败时，看**电脑上那个服务器窗口**有没有出现访问记录：
> - **有记录** → 网络通了，是文件名或路径问题
> - **没记录** → 是防火墙或 IP 问题

### Q5: `sha256sum: not found`

原厂固件里可能没有独立的 `sha256sum` 命令。先试 BusyBox 自带 applet：

```sh
busybox sha256sum /tmp/rt3bcwrite /tmp/factory.ubi
```

输出仍须与第 3.2 节的两个 SHA-256 完全一致。
如果这条命令也不可用，**停在这里，不要仅凭文件大小继续刷写**；
先找可在原厂系统运行的 SHA-256 校验工具并核对结果。

文件大小可以作为辅助检查：

```sh
ls -la /tmp/rt3bcwrite /tmp/factory.ubi
# rt3bcwrite 应该是 12287 字节
# factory.ubi 应该是 13107200 字节
```

### Q6: 重启后连不上 `192.168.10.1`

**最可能的原因：网线插在 WAN 侧。**

QSDK 的管理口**只绑 LAN**。解决：

1. 把网线插到 **RT3000 的 LAN 口**
2. 等电脑重新获取 IP（应该拿到 `192.168.10.x`）
3. 再访问 `http://192.168.10.1`

**另一个可能**：设备还在启动。首次启动较慢，多等 1 分钟。

**还有可能**：设备尝试启动 QSDK 但没起来，于是启动了原厂。
> ⚠️ **「启动失败后自动回退原厂」这条路径本教程未实测**，属于排查方向，不是已证事实。

检查方法：
- **按 MAC 扫描**两个网段，看设备出现在哪
- 如果能访问 `192.168.1.x` 的网页后台 → 设备在原厂系统里

### Q7: 我没接 WAN 口，会怎样？

**理论上可行**（不接 WAN 也能写入和启动），但：

- 设备可能拿不到网络，第 2 节的「电脑起服务器 + 设备 wget」方案就走不通
- 你需要另想办法把文件送进去（U 盘 / TFTP 等）

**建议**：按教程接好 WAN 口再做。

### Q8: 写入到一半断电了

**机制上，此时启动目标还指向原厂槽，所以重新上电应该会尝试启动原厂。**

> ⚠️ **但这个场景我们没有实测过**，属于机制推断，不能当作保证。

**重新上电后怎么做**：

1. **等待足够久**（原厂启动要 1 分钟以上）
2. **按 MAC 扫描**，看设备在哪：
   ```bash
   arp -a | grep -i "58:b3:8f"      # Linux/macOS
   arp -a | findstr "58-b3-8f"      # Windows
   ```
3. **根据结果判断**：

| 现象 | 说明 | 下一步 |
|---|---|---|
| 能访问原厂后台（`192.168.1.x` 的 80/443） | 回到原厂了 | 重新执行第 4、5 节 |
| 能访问 `192.168.10.1` | QSDK 起来了（数据可能不完整） | 用第 7 节验收，不合格就重装 |
| 两者都不通 | 需要排查 | 见[第五部分](05-RECOVERY.md) |

> 🔴 **如果两者都不通，就需要 TTL 串口救援** —— 参见第五部分第 3 节。

### Q9: 怎么退回原厂？

**在 QSDK 里**（一条命令）：

```sh
rt3slot oem --reboot
```

**这会**：切 selector 到原厂 → 重启 → 进入原厂系统。
**不会**：删除 `mtd16` 里的 QSDK 数据。
切回 QSDK 的前提是 `mtd16` 内容完好、且当时有一个能执行命令的系统。

> 详见后续的「双向切换」部分。

## 附录：为什么这样是安全的

### A.1 双槽位设计

设备固件（U-Boot）**只认一个 40 MB 的 UBI 容器**，
由 selector 决定它**映射到哪块物理区域**：

```
selector = 0  →  指向 mtd15（原厂）
selector = 1  →  指向 mtd16（QSDK）
```

所以切换系统**只需要改 selector 那 4 个字节**。

### A.2 写入顺序的保护作用

```
① 确认在原厂槽
② selector → 原厂      ← 保命点
③ 写 mtd16
④ 校验
⑤ selector → QSDK      ← 只有校验通过才切
⑥ 重启
```

**在 ② 和 ⑤ 之间，设备的启动目标是「原厂」。**
如果此时断电或写入失败，机制上重新上电应尝试启动原厂系统；
**断电场景尚未实测，不能保证一定能启动**。重新上电后应先确认实际运行的系统，
再按上文 Q8 的步骤处理。

### A.3 selector 的双副本冗余

selector 存在**两个地方**（`mtd2` 和 `mtd3`），互为备份。
写入工具的逻辑是：

```
写副本一 → 立即读回校验
写副本二 → 立即读回校验
最后再整体校验一次
```

**任何一步失败都会报 `RESULT=FAIL`**，此时**不要重启**。

### A.4 我们没有动的东西

| 项 | 状态 |
|---|---|
| `mtd15`（原厂系统） | ✅ 全程未写 |
| 其它分区（bootloader / 环境变量等） | ✅ 未碰 |
| U-Boot 持久化环境 | ✅ 未执行任何 `saveenv` |
