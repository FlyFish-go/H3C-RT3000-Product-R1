# RT3000 刷机教程 · 第五部分：救援

[← 教程总览](INSTALL.md)

> **适用范围**：仅在 RT3000 Machine-B（`GD5F1GQ5REYIG` NAND、原厂软件版本 `RT3000V100R005`）验证。A/C 样机以及 RW3000、RC3000、NX30 请勿套用镜像或刷写命令；无法确认硬件时先停下。


> **本部分目标**：设备出问题时怎么办。
>
> ⚠️ **本部分区分「已验证」和「未验证」的方案** —— 请特别注意标注。
> **第 1、2 节仅在能进入某个 Linux 系统时可按条件操作；第 3 节是未完成实机闭环的救援研究方向，不是可直接照抄的 NAND 恢复步骤。** 两个系统都无法操作时先保留现场，勿凭示例命令改动 bootloader、分区表或 `mtd15`。

## 0. 先判断问题严重程度

### 0.1 分级

| 级别 | 现象 | 严重程度 | 对应章节 |
|---|---|---|---|
| **①** | QSDK 起不来，但**能进原厂** | 🟢 轻 | [第 1 节](#1-第一层救援切回原厂) |
| **②** | QSDK 坏了，想在原厂里**重装** | 🟡 中 | [第 2 节](#2-第二层救援重装-qsdk) |
| **③** | **两个系统都起不来** | 🔴 重 | [第 3 节](#3-第三层救援u-boot-tftp需-ttl-线) |
| **④** | 只是想**回原厂用** | 🟢 轻 | [第 1 节](#1-第一层救援切回原厂) |

> 原厂槽 `mtd15` 在本方案中不被写入，保留了重要的救援条件。
> 但两个系统都无法访问也可能由供电、接线、启动选择器或启动链问题造成，
> **不能仅据此认定原厂槽损坏**。

### 0.2 第一步永远是：先看设备在哪

**不要急着操作，先判断设备现在什么状态。**

```bash
# 1. 按 MAC 找设备
arp -a | grep -i "58:b3:8f"          # Linux/macOS
arp -a | findstr "58-b3-8f"          # Windows

# 2. 找到了？测端口
#    有 22/7681  → QSDK 在运行
#    有 23/443   → 原厂在运行
#    什么都没有  → 先排除供电、接线和地址变化，再看第 3 节
```

**如果 ARP 表里没有**，先扫一遍网段：

```bash
# Linux（把网段换成当前实际网段，并分别检查上游和 QSDK LAN）
nmap -sn 192.168.1.0/24 && arp -a | grep -i "58:b3:8f"

# Windows
for /L %i in (1,1,254) do @ping -n 1 -w 100 192.168.1.%i >nul
arp -a | findstr "58-b3-8f"
```

> 📌 **两个网段都检查**：`192.168.10.x`（QSDK）和上游实际网段（原厂）。
> 上面的 ping / nmap 扫描只是帮助填充 ARP 缓存；设备不回应 ICMP 不代表已经离线。
> Windows 示例也要把 `192.168.1.%i` 换成 `192.168.10.%i` 再查一次。
> 端口开放情况只是线索，不能单独证明当前运行的系统。

## 1. 第一层救援：切回原厂

> **适用**：QSDK 有问题，但你现在还能操作 QSDK（SSH、TTYD，或已确认进入 QSDK Linux shell 的 TTL 串口）。
> 如果已确认设备正在运行原厂系统，就不需要再执行切换命令。

### 1.1 方法：一条命令

```sh
rt3slot oem --reboot
```

**这会把启动目标切到原厂并重启。**

**详细步骤见** → [第三部分第 2 节](03-SWITCH-SYSTEMS.md#2-qsdk-原厂)

### 1.2 如果 QSDK 已经进不去

**先别急着下结论** —— 需要确认设备到底在哪。

> ⚠️ **「切到 QSDK 后启动失败会自动回退原厂」这条路径本教程未实测。**
> 所以「QSDK 进不去」**不等于**「设备一定回原厂了」。
> 也可能两个系统都没起来 —— 那就要走第 3 节的串口救援。

**检查方法**：
1. **按 MAC 扫描两个网段**（`192.168.10.x` 和上游网段）
2. 如果能访问 `192.168.1.x` 的 H3C 网页后台（端口 80/443）→ **设备在原厂系统里**
3. 如果两个网段都找不到 → 先核对供电、网线与 DHCP 租约，再按第 3 节排查

**为什么「可能」回到原厂**？
回顾[第二部分 0.2 节](02-INSTALL-QSDK.md#02-有哪些保护机制以及它们的边界)和
[第四部分：固件升级](04-FIRMWARE-UPGRADE.md)：

> 写入 QSDK 之前，selector 会先被切到**原厂**。
> 只有写入并校验通过后，才切回 QSDK。
> **所以写入阶段失败时，设备会尝试启动原厂。**
>
> ⚠️ **但这个「自动回退」我们没有实测过** —— 属于机制推断，**不是已证事实**。
> 如果设备确实没起来，**先按本文第 0.2 节确认它到底在哪**，
> 找不到就走第 3 节的串口救援。

## 2. 第二层救援：重装 QSDK

> **适用**：设备在原厂系统里，想把 QSDK 重装/修复。

### 2.1 就是重走一遍第二部分

能进入原厂 root shell 后，按[第二部分：安装 QSDK](02-INSTALL-QSDK.md)的完整流程逐项核对。
原厂 telnet 畅通只是进入 shell 的条件之一；仍须确认实际运行系统、分区和 selector、
`mtd16` 的 UBI 映射、镜像哈希与写入前检查。**重装会擦除现有 QSDK 配置，确认目标后再执行擦写。**

### 2.2 如果原厂 telnet 不通

**场景**：原厂的配置被改坏了（例如导入了一个错误的配置文件），
或者你不确定原厂 telnet 为什么不通。

> ⚠️ **注意区分**：
> - **`sysupgrade -n`** 只能重置 **QSDK 的配置**（它操作的是 `mtd16`）。
>   **它不会、也不能重置原厂配置。**
> - 重置**原厂配置**须先确认当前运行原厂，再用原厂网页后台的方法。

**解决**：先恢复原厂配置，再用[第一部分](01-GET-TELNET.md)的方法**重新开一次 telnet**。

需要：
1. 能进原厂网页后台（`http://<原厂IP>`）
2. 用 `一键开启telnet.bat` 改配置
3. 导入配置

> ⚠️ **如果连原厂网页后台也进不去**，先用运行中的系统身份、接线和 IP 证据排查。物理 Reset 的作用取决于**当前运行的系统**；在 QSDK 中按键会清除 QSDK 配置，不能用它重置未运行的原厂槽。本教程没有对原厂 Reset 按键做本轮复走，不能把长按时间和结果当作已验证救援步骤。

### 2.3 重装会丢失 QSDK 的配置吗

**会。** `ubiformat` 会擦除整个 `mtd16`，包括配置卷。

**要保留配置** → 用 `sysupgrade`（见[第四部分](04-FIRMWARE-UPGRADE.md)），
但前提是 **QSDK 还能启动**。

> **选择路径**：
> - QSDK **能**启动 → 可按第四部分用 `sysupgrade` 保留配置升级。
> - QSDK **不能**启动、但能进原厂 root shell → 可按第二部分重装；这会清除 QSDK 配置。
> - 两个系统都不能操作、但 U-Boot 仍可运行 → 第 3 节的 initramfs 路径仅是方向性指引，完整 NAND 救援尚未实测；先保留现场并请熟悉该设备的人员评估。

## 3. 第三层救援：U-Boot + TFTP（需 TTL 线）

> **适用**：**两个系统都起不来**。
>
> ⚠️ **本节的完整流程尚未在本项目上端到端验证** ——
> 我们验证过的是「在 U-Boot 里通过网络加载 initramfs 启动」，
> 但「从 U-Boot 直接恢复 NAND」的完整路径**未实证**。
> 请把本节作为**方向性指引**，遇到问题需进一步排查。

### 3.1 需要什么

| 物品 | 说明 |
|---|---|
| **USB-TTL 串口线** | 3.3V，用于看串口输出、进 U-Boot |
| 网线 | 连接 TFTP 服务器与设备；本项目 RAM 启动实测走通的是 RT3000 的 WAN 路径，实际接法须先确认 |
| TFTP 服务器 | 电脑上运行（Windows 可用 Tftpd64） |
| 固件文件 | `factory.ubi` 或 initramfs |

### 3.2 串口接线

RT3000 主板上有串口焊盘（**需要拆机**）。

| 项 | 值 |
|---|---|
| 波特率 | **115200** |
| 数据位/停止位/校验 | 8 / 1 / 无 |
| 电平 | **3.3V**（不要用 5V） |

> ⚠️ **本教程不提供拆机接线图**。请自行确认焊盘位置，或参考社区资料。

### 3.3 进 U-Boot

**关键**：U-Boot 的自动启动等待**只有 1 秒**。

```
****************************************************************************
*                                                                          *
*                       H3C RT3000 Boot, Version 100                       *
*                                                                          *
****************************************************************************

Hit Enter to stop autoboot:  1     ← 只有 1 秒！
```

**做法**：
1. 打开串口终端
2. **给设备上电的同时，连续快速敲回车**
3. 看到 `<H3C>` 提示符就成功了

> 💡 如果抢不到，可以先按住回车不放再上电。

### 3.4 U-Boot 里能做什么

**本项目已验证的范围**：

| 能力 | 说明 |
|---|---|
| TFTP 与内存启动 | 在本机已通过 U-Boot 网络加载 initramfs 并启动；当时使用 WAN 路径 |

U-Boot 的 UBI attach/读取及从临时系统修复 NAND 未在本教程的完整救援流程中验证。

**结合使用**：通过 TFTP 加载一个 **initramfs 镜像**到内存启动，
得到一个临时的 Linux 环境，然后从那里修复 NAND。

### 3.5 initramfs 救援的大致流程

> ⚠️ **以下是方向性描述，不是逐条验证过的步骤。**

```
① 电脑上运行 TFTP 服务器，放好 initramfs 文件
② 串口进 U-Boot
③ 配置 U-Boot 网络（setenv ipaddr / serverip）
④ tftpboot 加载 initramfs 到内存
⑤ bootm 启动
⑥ 进入临时 Linux 环境
⑦ 在临时环境里修复 mtd16（或切换 selector）
⑧ 重启
```

**关键点**：在 U-Boot 本身能运行、TFTP 加载成功的前提下，
这个临时系统运行在**内存**里，不依赖 `mtd15` 或 `mtd16` 的系统镜像。

### 3.6 所需文件

| 文件 | 用途 |
|---|---|
| `initramfs-fit-uImage.itb` | 临时救援系统 |
| `factory.ubi` | 用于重写 `mtd16` |

**r5 版本**：

| 文件 | SHA-256 |
|---|---|
| initramfs | `65a374d29ab533788e2b51e96878ace57c582034a1ce2f8329747cd78a043a31` |
| factory.ubi | `80e99811887ec3bedaf648a32954d93fc5e1482ab70605d6e41d791ce181c529` |

### 3.7 ⚠️ 千万不要做的事

| 禁止 | 原因 |
|---|---|
| ❌ **不要 `saveenv`** | 会写入 U-Boot 持久化环境，可能覆盖关键变量 |
| ❌ **不要擦除 `mtd15`** | 那是最后的退路 |
| ❌ **不要写 bootloader 分区** | 写坏了就真变砖了 |
| ❌ **不要改分区表** | 同上 |

> **原则**：在 U-Boot 里，**只做「读取」和「启动」，不做「写入」**。
> 需要写的时候，先启动到临时系统里去写。

## 4. 你的备份资产

### 4.1 应该有的备份

| 备份 | 内容 | 重要性 |
|---|---|---|
| **原厂系统镜像** | `mtd15` 的完整 dump（40 MB） | ⭐⭐⭐ 最重要 |
| **原厂配置备份** | 网页后台导出的 `.cfg` | ⭐⭐ |
| **QSDK 产物** | `factory.ubi` / `sysupgrade.bin` | ⭐⭐ |
| **selector 工具** | `rt3bcwrite` | ⭐⭐ |

### 4.2 原厂系统的备份 —— 请自己做一个

> ⚠️ **本教程不附带任何现成的备份文件。**
>
> 原因：原厂镜像可能包含设备独有的配置或身份信息。
> **别人的备份不能当作你这台设备的恢复镜像，甚至可能有害。**
>
> **必须从你自己的设备上导出。**

#### 为什么要备份

`mtd15` 是原厂系统。虽然本方案的流程**不写它**，但：

- 万一误操作写到了它，没有备份就无法恢复
- 有了备份，最坏情况下还能尝试恢复原厂

#### 怎么备份

**前提**：设备在原厂系统里，有 root shell。本节的完整备份传输命令
**尚未按最终教程逐条实机复走**。先确认原厂环境有 `dd`、`sha256sum`
（或 `busybox sha256sum`）及 `nc`；缺少必要工具时先停下。

```sh
# ① 先确认 mtd15 的大小
cat /proc/mtd | grep mtd15
# 期望: mtd15: 02800000 00020000 "..."
#       02800000 (hex) = 41943040 字节 = 40 MB

# ② 流式读取并计算源数据哈希，不在设备的 /tmp 暂存 40 MB 文件
dd if=/dev/mtd15 bs=4096 count=10240 | sha256sum
# 若没有独立 sha256sum，可试 busybox sha256sum

# ③ 确认 dd 报告完整读取 10240 个块，再记下哈希
```

#### 怎么把备份传到电脑

**40 MB 用 `/tmp`（内存盘）可能不够。** 下面是需要 `nc` 的流式传输示例，
传输完还必须核对大小和哈希；不同 `nc` 实现的监听语法可能不同。

> ⚠️ 原厂分区或配置备份可能包含设备唯一身份与凭据。只传到可信电脑，妥善加密保存，不要作为公开 Issues 附件或提交进源码仓库。

**电脑上先监听**（Linux/macOS）：

```bash
nc -l -p 9000 > mtd15-backup.bin
```

**设备上发送**：

```sh
dd if=/dev/mtd15 bs=4096 count=10240 | nc <电脑IP> 9000
```

**电脑上校验**：

```bash
sha256sum mtd15-backup.bin
wc -c < mtd15-backup.bin
# 哈希应与设备端读出的完整哈希一致；大小应为 41943040 字节
```

> 💡 **Windows 用户**：可以用 `nc`（ncat，来自 Nmap）或
> Tftpd64 等工具接收。也可以用 U 盘挂载后 `cp`。

#### 备份好后

| 项 | 记下来 |
|---|---|
| 文件位置 | 你的电脑/移动硬盘上的路径 |
| **SHA-256** | 设备端源数据与电脑端文件一致的值 |
| 备份日期 | |

> ⚠️ **建议再复制一份到别处**（NAS / 移动硬盘）。
> 只有一份的备份不算备份。

### 4.3 恢复 mtd15（危险操作）

> 🛑 **这是最后手段。恢复原厂槽意味着覆盖原厂系统。**
>
**本项目不提供、也不执行 `mtd15` 写入命令。** 保留原机备份及哈希，
交由具备该设备恢复经验的人员评估。备份完好也不保证故障一定来自原厂槽。

## 5. 预防措施

### 5.1 刷机前

| 措施 | 说明 |
|---|---|
| ✅ **备份 mtd15** | 最重要的一件事 |
| ✅ **备份原厂配置** | 网页后台导出 `.cfg` |
| ✅ **确认哈希** | 所有文件下载后都校验 |
| ✅ **准备好 TTL 线** | 万一需要救援 |
| ✅ **别在雷雨天刷** | 减少断电风险 |

### 5.2 操作中

| 措施 | 说明 |
|---|---|
| ✅ **不要中断写入** | `ubiformat` / `sysupgrade` 过程中别断电 |
| ✅ **看清确认项** | 特别是 `RESULT=PASS` 和 `RESULT=FAIL` |
| ✅ **不要跳步** | 特别是「保命检查」（第二部分第 4 节） |

### 5.3 出问题时

| 原则 | 说明 |
|---|---|
| 🧘 **先冷静** | 多数情况可以恢复，但**需要串口线才能应对最坏情况** |
| 📋 **先取证** | 记下完整输出，别急着重试 |
| 🔍 **先判断** | 确认设备现在在哪（见 0.2 节） |
| 🚫 **别乱试** | 不清楚的命令不要执行，尤其是写入类的 |
