> ```sh
> # 在原厂 telnet 里
> cat /proc/mtd              # 看分区表和大小

>
> **如果你的输出和上表不符，请先停下** ——

### 怎么确认自己是 Machine-B

原厂启动日志（串口）里会显示：

```
     Description:  ARM OpenWrt qcom-ipq50xx-mpxx device tree blob
   Using 'config@mp02.1' configuration            ← mp02 = Machine-B
```

以及 NAND 识别行：

```
Serial NAND device Manufacturer:GD5F1GQ5REYIG
```

**免 TTL** 指正常安装和双向切换时无需串口操作，**不免除刷写前确认硬件**。`cat /proc/mtd` 与 `uname -r` 只能核对布局和原厂内核，不能单独证明 NAND 型号及启动配置。若没有可信的启动日志、硬件标识或既有设备记录来确认上述 Machine-B 配置，先停在只读核对阶段，不要仅凭设备外壳上的“RT3000”执行写入。

```
     上游路由器（提供 DHCP）
          │
    ┌─────┴──────┐
    │  RT3000    │

## 这个设备有什么特别的

### 两个系统槽位

RT3000 的 NAND 里有**两个独立的 40 MB 系统槽位**：

| 槽位 | 分区 | 内容 |
|---|---|---|
| A | `mtd15` | **原厂系统**（出厂就有） |
| B | `mtd16` | **QSDK**（我们装的） |

**selector**（选择器）决定下次从哪个槽启动：

```
selector = 0  →  启动原厂
selector = 1  →  启动 QSDK
```

### 三个重要特性

**① 切换是免费的**

因为两个系统**同时存在**，切换只更新 `mtd2`、`mtd3` 中各一份 4 字节的 selector 字段 ——
不需要重新刷机，不会丢配置。

**② 原厂系统槽位保留**

我们**从头到尾不写 `mtd15`**，因此原厂槽内容保留。
这不证明它在任何故障后一定可启动；「切回去」仍需要能执行命令的环境 —— 详见下方边界说明。

**③ 写入有失败保护**

安装/升级 QSDK 时，流程是：

```
先把 selector 切到原厂  ← 保命
    ↓
再写入 mtd16
    ↓
校验通过后才切回 QSDK
```

**所以写入阶段失败时，设备会尝试启动原厂。**

> ⚠️ **但这条「自动回退」路径我们尚未实测。**
> 详见下方[安全说明的边界](#安全说明的边界重要)。

## 安全说明的边界（重要）

本方案有多重保护，但**保护机制不等于「一定救得回来」**。
发布者已实测和未实测的部分，明确区分如下：

### 已实测

| 能力 | 验证方式 |
|---|---|
| 从原厂安装 QSDK 到 `mtd16` | ✅ 完整走通 |
| 从 NAND 启动 QSDK | ✅ |
| **主动双向切换**（切换命令更新 selector） | ✅ QSDK 配置文件哈希保留；原厂 telnet 设置跨切换仍有效 |
| 保留配置升级（`sysupgrade`） | ✅ |
| 重置 QSDK 配置（`sysupgrade -n`） | ✅ |
| 切换后 QSDK 所测配置文件逐字节保留 | ✅；不代表两边所有配置都经过逐字节核对 |

### 🔴 未实测 / 无法保证

| 事项 | 实际状态 |
|---|---|
| **切到 QSDK 后启动失败，是否自动回退原厂** | **未验证**。机制上 U-Boot 会读 selector，但失败时的具体行为未实测。 |
| **写入/升级过程中断电** | **未实测**。机制上启动目标仍指向原厂，但这只是推断。 |
| **原厂内容完好 ⇒ 无需串口就能切回** | **不成立**。切回需要能运行命令的环境；两个系统都起不来时必须用串口。 |
| **两个系统都无法启动** | 需要 **TTL 串口 + U-Boot**（第五部分第 3 节）。该路径**未端到端验证**。 |

### 结论

> **保护机制降低风险，但不能替代两件事：**
> 1. **备份**（尤其 `mtd15` 的完整镜像）
> 2. **串口救援的准备**（TTL 线）

## r5 版本说明（推荐使用）

| 项 | 值 |
|---|---|
| 系统 | OpenWrt 21.02.7 |
| 内核 | Linux 5.4.164 |
| 界面 | 中文 LuCI |
| 默认 LAN | `192.168.10.1` |
| 默认 WiFi | `RT3000` / `RT3000-5G` |
| WiFi 密码 | `RTRCRWNX` |

### r5 修了什么

**r4 版本实测存在 WiFi 关联问题**：设备能广播、客户端能认证、能关联，
但**无法完成密钥握手** —— 表现为「连不上 WiFi」、反复重连。

> ⚠️ **说明**：这个问题**并非所有历史版本都存在**。
> 更早的测试版本（candidate9）有真实客户端成功关联并跑出吞吐的记录
> （`rx bytes` 368 MB、速率 1921.5 Mbit/s）。
> **为什么某些版本正常、r4 不正常，原因尚未完全确定。**
> r5 已通过修复补丁消除了该现象。

**根因**：ath11k 驱动声明了 `VLAN_OFFLOAD` 能力，
导致 hostapd 在每次关联时多发一个内核不接受的属性值，
整条设置命令被内核拒绝。

**修复**：让 hostapd 在「不绑定 VLAN」的情况下不发送该属性。

> 实测验证：修复后两个频段都能正常连接、能上网、能断开重连、能双频切换。
