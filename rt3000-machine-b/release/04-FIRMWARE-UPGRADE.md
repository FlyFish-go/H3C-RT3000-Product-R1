# RT3000 刷机教程 · 第四部分：固件升级

[← 教程总览](INSTALL.md)

> **适用范围**：仅在 RT3000 Machine-B（`GD5F1GQ5REYIG` NAND、原厂 `RT3000V100D009`）验证。A/C 样机以及 RW3000、RC3000、NX30 请勿套用镜像或刷写命令；无法确认硬件时先停下。


> **本部分目标**：把 QSDK 更新到新版本（例如 r4 → r5）。
>
> **前置条件**：设备正在运行 QSDK。
>
> **本部分会重写 `mtd16`，并更新 `mtd2`、`mtd3` 中的启动 selector；不写原厂固件分区 `mtd15`。**

## 0. 什么时候需要升级

| 场景 | 需要升级吗 |
|---|---|
| 从旧版本换到新版本（如 r4 → r5） | ✅ |
| 修了某个 bug 后想用上 | ✅ |
| 想恢复出厂设置 | ✅（用 `-n`，见第 3 节） |
| 只想在原厂和 QSDK 之间切换 | ❌ **不需要** —— 见[第三部分](03-SWITCH-SYSTEMS.md) |

> ⚠️ **重要区别**：
> **「升级」会重写 QSDK 槽**；**「切换」只改 selector**。
> 如果只是想在两个系统间来回切，**不要升级**。

## 1. 准备升级包

### 1.1 获得升级包

**升级包文件名的特征**：包含 `sysupgrade`，例如：

```
openwrt-ipq50xx-arm-h3c_rt3000-squashfs-nand-sysupgrade.bin
```

> ⚠️ **注意区分两种文件**：

| 文件名包含 | 用途 | 用在哪 |
|---|---|---|
| `factory.ubi` | **首次安装** | 第二部分（`ubiformat` 写入） |
| `sysupgrade.bin` | **升级** | **本部分** |

**用错了会怎样**：
- 升级时用 `factory.ubi` → 可能失败或出问题
- 首次安装时用 `sysupgrade.bin` → 不行（那个需要已有系统在跑）

### 1.2 r5 升级包

| 项 | 值 |
|---|---|
| 文件 | `r5-sysupgrade.bin` |
| 大小 | 12,299,027 字节 |
| SHA-256 | `7f8f9e5dca42bc0b1fdb0c5dc9d01f8863878631202d2d325df6cd659bf1d65a` |

### 1.3 传到设备

和第二部分一样，用**电脑起文件服务器 + 设备 wget** 的方式：

**电脑上**（工具包里的 `1-启动文件服务器.bat`，把 `.bin` 也放在同目录）：

> 📌 这个批处理文件启动前**要求目录里有一个 `.ubi` 文件**；即使这次只升级，也要保留第二部分用的 factory 镜像供脚本检查，**不要在设备上下载或写入它**。
> 脚本会自动识别 `.ubi`，但 **`.bin` 需要在下方 `wget` 命令里手写文件名**。
> 把升级包命名为 `r5-sysupgrade.bin`，或准确记录它的原始名字；选对脚本显示的电脑 IP。

**设备上**（QSDK 的 SSH 窗口）：

```sh
cd /tmp
wget http://<电脑IP>:8899/<升级包文件名> -O /tmp/sysupgrade.bin
```

### 1.4 校验

```sh
sha256sum /tmp/sysupgrade.bin
```

**必须与 1.2 节的哈希一致。**

```sh
ls -la /tmp/sysupgrade.bin
# 大小应为 12299027
```

先做不写入的镜像与设备检查：

```sh
sysupgrade -T /tmp/sysupgrade.bin
echo "IMAGE_CHECK_RC=$?"
```

应看到 `RT3000 Machine-B sysupgrade image verified` 且 `IMAGE_CHECK_RC=0`。
这只能证明当前检查门槛通过，不能替代升级后的写入读回验收；检查不通过就不要执行下节的升级命令。

## 2. 保留配置升级

> **这是最常用的方式** —— 升级后 WiFi 密码、网络设置等都保留。

### 2.1 执行

```sh
sysupgrade /tmp/sysupgrade.bin
```

> 📌 **注意**：是 `sysupgrade`，不是 `ubiformat`。
> 这是 OpenWrt 的标准升级命令，它会自动处理「写入 + 切换 + 重启」。

### 2.2 期望输出

```
RT3000 Machine-B sysupgrade image verified
Tue Sep 22 14:21:30 UTC 2026 upgrade: Saving config files...        ← 配置已备份
Tue Sep 22 14:21:30 UTC 2026 upgrade: Commencing upgrade. Closing all shell sessions.
Connection to 192.168.10.1 closed by remote host.
```

**关键那一行**：

```
upgrade: Saving config files...
```

**看到它只说明配置备份步骤已开始，不能单凭这行确认升级后配置已保留。**
必须在重启后按 2.4 节核对实际配置。
（用 `-n` 升级时**不会**出现这一行，见第 3 节。）

### 2.3 然后会自动重启

**SSH 会断开，这是正常的。**

**等待 1~2 分钟**，然后验证。

### 2.4 验证

```sh
ssh root@192.168.10.1

# 1. 系统起来了
uname -r                                  # 5.4.164
cat /etc/openwrt_release | grep RELEASE   # 21.02.7

# 2. 配置还在：与升级前保存的 SHA-256 对比
sha256sum /etc/config/wireless
# 不要把包含 Wi-Fi 密钥的 uci show 输出贴到公开 Issues

# 3. 固件版本
rt3slot status | grep RUNNING_RELEASE

# 4. 两个槽位的工具门槛（校验范围见第三部分）
rt3slot verify oem
rt3slot verify qsdk
```

## 3. 不保留配置升级（QSDK 恢复出厂）

> **用途**：把 **QSDK** 恢复出厂设置（清空 QSDK 的所有配置，包括 WiFi 密码、网络设置）。
>
> ⚠️ **作用范围**：
> - ✅ 清空的是 **QSDK 的配置**（存在 `mtd16` 的 `rootfs_data` 卷里）
> - ❌ **不影响原厂系统**，也不影响原厂的配置
>
> **想重置原厂配置** → 先确认设备已经启动到原厂系统，再使用原厂网页后台的「复原」功能。当前运行 QSDK 时按物理 Reset 不能指定去清除另一个槽位的原厂配置；不要把它当作本命令的替代操作。

### 3.1 执行

```sh
sysupgrade -n /tmp/sysupgrade.bin
```

**多了一个 `-n`** —— 意思是 **不保留配置**（no-save）。

### 3.2 与保留配置的区别

| | 保留配置 | `-n` 不保留 |
|---|---|---|
| 命令 | `sysupgrade <file>` | `sysupgrade -n <file>` |
| 输出里有 `Saving config files...` | ✅ 有 | ❌ **没有** |
| WiFi 密码 | 保留 | **恢复默认**（`RTRCRWNX`） |
| LAN 地址 | 保留 | 恢复默认（`192.168.10.1`） |
| SSH 主机密钥 | 通常保留 | 可能重新生成；连接前核实设备身份 |
| 相当于 | 正常升级 | **QSDK 恢复出厂**（不影响原厂） |

### 3.3 验证

```sh
# 1. 配置已恢复默认
uci show wireless | grep '\.ssid='
# 期望: RT3000 / RT3000-5G；再用手机凭发布的默认密码实际连接

uci get network.lan.ipaddr
# 期望: 192.168.10.1

# 2. 之前设的测试项应该都没了
ls /etc/config/ | grep 你之前加的东西
```

### 3.4 ⚠️ SSH 主机密钥会变

用 `-n` 之后，SSH 会提示：

```
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
```

`-n` 后主机密钥可能重新生成，但相同警告也可能是连错设备或主机密钥冲突。
先用可信的设备身份信息核实当前连接目标，再更新本机记录。

**解决**：

```bash
ssh-keygen -R 192.168.10.1     # 确认目标身份后，才删除该地址的旧记录
ssh root@192.168.10.1          # 核对新指纹后再接受
```

## 4. 升级过程发生了什么

了解这个过程，有助于你判断**升级卡在哪一步、以及接下来该怎么办**。

### 4.1 完整流程

```
① 校验升级包
   └─ "sysupgrade image verified"

② 备份配置
   └─ "Saving config files..."      （用 -n 时跳过）

③ 停止所有服务

④ 切换到内存运行（ramdisk）
   └─ "Switching to ramdisk..."

⑤ 把 selector 切到「原厂」        ← ⭐ 保命点
   └─ RESULT=PASS both copies = 0x00000000

⑥ 分离并擦除 mtd16
   └─ ubi0: mtd16 is detached
   └─ ubiformat: 320 eraseblocks

⑦ 写入新的 QSDK
   └─ ubiformat: flashing eraseblock ... （进度行因版本而异）

⑧ 校验写入内容
   └─ "second-slot payload verified"

⑨ 校验通过 → 把 selector 切回「QSDK」
   └─ second-slot payload verified; QSDK selected

⑩ 重启
```

### 4.2 ⭐ 关键：第 ⑤ 步的保命作用

**注意第 ⑤ 步**：在擦除 `mtd16` **之前**，先把 selector 切到原厂。

**这意味着**：如果第 ⑥~⑧ 步中任何一步失败（断电、写坏、校验不过），
**设备的启动目标仍然指着原厂系统**。重新上电后应尝试启动原厂，
但断电场景尚未实测，不能保证正常启动；应按下文 Q8 核实实际状态。

**只有第 ⑧ 步校验通过，第 ⑨ 步才会把 selector 切回 QSDK。**

### 4.3 这个流程的意义

| 场景 | 结果 |
|---|---|
| 升级成功 | 重启进入新 QSDK |
| 升级中失败/断电 | selector 预期仍指向原厂；实际启动结果需核实 |
| 写入内容损坏 | 校验不通过 → 不切 selector；重启后核实实际系统 |

**不能把回到原厂当作必然结果。** 两个系统都无法访问时，按第五部分排查和救援。

### 4.4 升级写入范围

**固件载荷的写入目标是 `mtd16`** —— 从 `rt3000.sh` 的实现看，
它 `ubiattach` / `ubiformat` / `ubiupdatevol` 的都是 `mtd16`。
启动目标切换还会由 `rt3bcwrite` 修改 `mtd2`、`mtd3` 的 BOOTCONFIG selector；
升级流程不写 `mtd15`。

**可选的检查**（注意其局限）：

```sh
# 升级前后各执行一次，对比首块 UBI 序列号
dd if=/dev/mtd15 bs=1 skip=24 count=4 2>/dev/null | hexdump -C
```

> ✅ **能说明**：本次读取的这个字段，前后两次读到的值相同。
>
> ❌ **不能说明**：整个 40 MB 的 `mtd15` 一个字节都没变；
> 甚至**不能说明该块未被重写**（可能被写回了相同内容）。
> 若要得到更强的内容证据，需要在相同读取条件下比对完整可读数据，
> 并解释 UBI 元数据、坏块与读取路径带来的差异；
> 载荷校验的范围和局限见[第三部分 5.4 节](03-SWITCH-SYSTEMS.md#54-怎么确认切换没有重写固件)。
>
> 📌 **实践上**：升级过程不涉及 `mtd15` 是**从代码逻辑确认的**；
> 这个 4 字节检查只是一个低成本的旁证。

## 常见问题

### Q1: `sysupgrade: not found`

**原因**：你可能在**原厂系统**里。原厂没有 `sysupgrade`（它用的是厂商自己的升级机制）。

**确认**：

```sh
uname -r
# 5.4.164 → QSDK（有 sysupgrade）
# 4.4.60  → 原厂（没有）
```

**原厂怎么升级？** 用原厂网页后台的「软件升级」功能（本教程不涉及）。

---

### Q2: 升级后连不上了

**排查**：

| 检查 | 说明 |
|---|---|
| 等够时间了吗 | 首次启动 + 配置恢复可能要 2 分钟 |
| 网线在 LAN 口吗 | QSDK 管理口只绑 LAN |
| 是 `192.168.10.1` 吗 | 除非你改过，否则就是这个 |
| 用 `-n` 了吗 | 若用了，LAN 恢复默认 `192.168.10.1` |
| 切回原厂了吗 | 按 MAC 扫一下，看设备在不在 `192.168.1.x` |

**如果设备回到了原厂**：
> ⚠️ **这不一定说明「自动回退」生效了** —— 该路径未实测。
> 也可能是你手动切过原厂，或设备本来就在原厂。

如果确认升级后进入原厂，先保留日志、核对实际 selector 和 `mtd16` 状态，
查明失败阶段。`/tmp/sysupgrade.bin` 在重启后已经消失；可以核对电脑上保留的原文件，
但**不要仅凭源文件哈希就直接重试写入**。

---

### Q3: 升级后配置丢了

| 原因 | 情况 |
|---|---|
| 用了 `-n` | **正常行为** —— 那本来就是「不保留配置」 |
| 没用 `-n` 但配置还是丢了 | 少见。检查是否磁盘空间不足（`df -h /overlay`） |

---

### Q4: 升级包要放哪里？

**随便**（`/tmp` 是常见的，重启会清空）。

只要 `sysupgrade` 命令里的路径对就行。

> 💡 **注意**：`/tmp` 是**内存盘**，重启后会消失。所以升级包放 `/tmp` 不会占存储。

---

### Q5: 升级需要多久？

| 阶段 | 耗时 |
|---|---|
| 下载升级包（12 MB） | 几秒~几十秒（看网速） |
| 写入 NAND | 约 1 分钟 |
| 重启 + 启动 | 约 1 分钟 |
| **合计** | **约 2~3 分钟** |

---

### Q6: 能不能降级（刷回旧版本）？

**本教程没有验证通用降级流程。** 旧包还需通过当前设备的镜像检查，
且配置格式可能不兼容。保留配置的降级尤其不能直接照搬升级步骤。
操作前应备份当前配置、确认目标版本与硬件匹配，并先运行 `sysupgrade -T`；
测试通过也只代表包检查通过，不代表实际降级已获实机验证。

---

### Q7: `factory.ubi` 和 `sysupgrade.bin` 到底怎么选

| 你的情况 | 用哪个 | 命令 |
|---|---|---|
| 设备还没装过 QSDK（在原厂里） | `factory.ubi` | `ubiformat /dev/mtd16 -y -f ...` |
| QSDK 已经在运行，要更新 | `sysupgrade.bin` | `sysupgrade <file>` |
| QSDK 坏了，要重装 | `factory.ubi` | 先确认能进入原厂；若两个系统都起不来，按第五部分救援 |

**判断方法**：

```sh
uname -r
# 5.4.164 → QSDK 在运行 → 用 sysupgrade.bin
# 4.4.60  → 原厂 → 用 factory.ubi
```

---

### Q8: 升级过程断电了

**机制上，升级流程在擦写前会把 selector 切到原厂**（见第 4.2 节），
所以重新上电**应该**会尝试启动原厂。

> ⚠️ **断电场景我们未实测**，这是机制推断，不是保证。

**重新上电后**：

1. **等足够久**（原厂启动 1 分钟以上）
2. **按 MAC 扫描**确认设备在哪
3. 根据结果处理：

| 现象 | 下一步 |
|---|---|
| 进了**原厂** | 先查 selector、`mtd16` 和失败日志，再决定是否重试 |
| 进了**旧版 QSDK** | 先核对实际版本和槽位内容，不据此推断失败阶段 |
| **都进不去** | 先排除供电与接线问题，再按[第五部分：救援](05-RECOVERY.md)排查 |
